## Audit and bounded changes

The working B11 server transitions, snapshots, stock/OCC, Cart clearing and atomic award are retained. Real frontend gaps: React state busy alone cannot synchronously reject repeated callbacks; restored contexts were set only after successful GET; known-create-ID read failures could select a fresh key while an old terminal Order still occupied UI state; Cart reload failure was mistaken for ambiguous payment; payment button omitted the final amount; cancelled/error/disabled explanations and input/select focus/summary structure needed refinement.

OrderCheckout now uses a synchronous in-flight ref, restoration loading/Cart lock, current-session/mount/read-sequence guards, contexts primed before GET, known Order ID read-only recovery and separate Cart-refresh state. Original create/payment key/payload retained across ambiguous response/GET outage/reload; no automatic new key or business retry. Saved previewSubtotal is non-authoritative UI metadata used only to flag price drift; server snapshot remains the payment amount. Order summary labels size/topping names and prices/qty/unit/line/subtotal/fixed discount/code/final VND amount. Native labeled select/input, amount on payment action, semantic definition list/status/alert/busy, focus-visible/min44px and scoped wrapping styles retain the existing theme.

## Acceptance criteria

Cart cache load reports whether the response was accepted under its existing session/revision guards. Checkout acknowledges a Cart update only on acceptance; a superseded successful read followed by a newer failed read retains the last cache and requests a readonly refresh. This internal frontend signal changes no API contract.

- Authenticated nonempty Cart creates PENDING and shows immutable backend snapshot before any payment; empty Cart cannot start a new create, while original cached retries remain allowed even when current Cart is empty/unavailable.
- WALLET/CARD action confirms displayed Order.total; only current backend GET/accepted cancellation response supplies state. No fake PAID or real card fields.
- Success: PAID/paidAt, one Payment/award/balance effect, purchased Cart clear/unlock, no second stock claim. Failure: FAILED/PAYMENT_FAILED, stock restore once, Cart preserve/lock, zero award.
- Failed retry uses same Order snapshot, new key for new business attempt, stock OCC reacquisition; protocol stock rejection preserves failed Order/Cart/points and creates no Payment. Cancel PENDING restores once; cancel FAILED never double-restocks.
- Repeated same-frame handlers cause one POST; network/timeout/committed response loss preserves original key/payload. Known create ID retry only GETs. GET recovery outage does not lose cached operation or permit editing/new payment. A resolved payment plus failed Cart refresh keeps current state and asks readonly refresh, without charging again.
- Vietnamese actionable empty/config/stock/stale Cart/existing unpaid/promotion/auth/declined/server/unknown messages preserve selections and never expose raw backend errors. Unknown payment disables method change/cancel; terminal Orders offer no new payment/customer paid-cancel.
- PENDING/FAILED/PAID fit390/768/1366, labeled controls and keyboard focus/Tab/Enter actions work, status/errors announced and reduced-motion respected.

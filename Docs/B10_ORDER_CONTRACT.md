## Transaction, OCC and idempotency

Syntax/auth before transaction; normalized request hash independent of DB prices/Cart state. In transaction: completed claim lookup/replay first; short user-row FOR UPDATE lock; claim CREATE_ORDER insert; active-order guard; current Cart equality; B09 current DB validation/pricing; sorted aggregate product CAS decrement (id/version/stock>=qty), version+1/updated_at; create PENDING/items/topping snapshots; save201 response/completed claim. Commit together; failures roll back claim, stock, Order/items and leave Cart. Lock before FK claim insert avoids concurrent key-share→update lock upgrade deadlocks. Different users still race stock using OCC; no inventory lock/reservation/TTL/queue or auto transaction retry.

Pool maxWait50ms/transaction400ms; local DB lock200ms/statement300ms. On unique/transaction failure rollback first, single new-transaction read of completed claim; replay if committed, otherwise409 IDEMPOTENCY_IN_PROGRESS for recognized create conflicts/timeouts,503 sanitized technical failure. Same user+operation+key+normalized payload returns exact historical201 body/Idempotency-Replayed:true; different payload409 IDEMPOTENCY_KEY_REUSED. Replay independent of current active order/catalog/Cart. Key scoped per user/operation, not cross-owner. Stock CAS count0 returns409 CONCURRENT_UPDATE without retry.

New key while active unpaid exists409 INVALID_ORDER_STATE with error.details.existingOrderId of owner only. Cart POST/PATCH/DELETE use same user-row lock/guard and same409 discovery, GET still allowed and DTO unchanged. No global unique-index/schema change: single locked service write path enforces active limit; future Payment must participate in same serialization.

## Cancel and future payment contract

PENDING cancel: user lock/ownership; order status+version CAS; aggregate immutable item quantities by product, sorted stock/version CAS restore+version increment/updated_at; CANCELLED snapshot/detail commit atomically. Bounds/any fault rollback all. Repeated CANCELLED no-op, no second restore. PAYMENT_FAILED cancel does not restore because later payment-failure transaction must already have restored once. Cart never modified by create or cancel, write lock lifted at CANCELLED.

Next phase: PENDING holds stock/locks Cart. Failure restores exactly once, keeps Cart and PAYMENT_FAILED lock. Retry re-checks/re-acquires stock using Order snapshot, not current Cart price. Success PAID clears consumed CartItems/unlocks; Loyalty follows its phase policy. B10 does not execute those transitions. Close tab/logout never releases PENDING stock.

## Frontend

Cart embeds Place Order/current snapshot/cancel; loading and safe validation/stock/promotion/API errors. Request key/payload/userId/orderId saved before POST in sessionStorage, no JWT; retry uncertain result keeps key/payload. Known rejection reloads Cart for customer confirmation. Response replay followed by GET current order. Backend existingOrderId restores flow without storage; controls disabled after active order discovery, backend enforces even before frontend knows. Cache-loss recovery happens on attempted checkout or blocked Cart write, no create probe on mount. GET /cart alone intentionally does not expose active-order metadata. Cancel opens Cart editing without clearing items. Summary never claims payment success; payment button remains historical disabled placeholder.

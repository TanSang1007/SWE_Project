POST /payments: JWT owner + mandatory Idempotency-Key (1..128 visible ASCII), strict body {orderId UUID, method WALLET|CARD}. No userId/amount/status/card data/client outcome. Cross-owner/missing order404 ORDER_NOT_FOUND. Server-only PAYMENT_MOCK_MODE=SUCCESS (default) or FAILURE, validated at startup; restart after changing configuration. Tests inject the mock result; no delays/external charge/provider/webhook.

HTTP200 for committed business result: payment id/orderId/status/amount string/method, failureCode MOCK_DECLINED only on FAILED; order id/orderCode/status; loyalty.awardedPoints. Success: SUCCEEDED/PAID/points. Failure: FAILED/PAYMENT_FAILED/zero, no award row. GET detail supplies current paidAt/earnedPoints/paymentStatus. Replay is historical, UI reads GET current order before confirmation. Total zero uses the same mock and success writes a zero-point award.

Ownership and replay precede current business-state checks. Same user + PAY_ORDER + key + normalized payload replays committed200/body with Idempotency-Replayed:true; payload changed409 IDEMPOTENCY_KEY_REUSED; failed replay does not create a new attempt. New business attempt uses new key on same order. CREATE_ORDER namespace independent. Claim PROCESSING never commits alone. Lock same user row before FK-bearing claim insert; reread claim/order after lock. Business effects and completed response commit together. On technical rollback, one recovery transaction reads committed claim; no automatic business retry. Recognized concurrency/timeout without result409 IDEMPOTENCY_IN_PROGRESS; other technical faults503 PAYMENT_UNAVAILABLE, never a fabricated business decline.

PENDING already owns aggregate snapshot stock: success never decrements again. Failure transitions via status/version CAS, records FAILED, restores aggregate snapshot qty once with stock/version CAS + increment/updatedAt, keeps Cart unchanged/locked. New retry on PAYMENT_FAILED reacquires stock with qty/stock/version OCC, transitions through PENDING, then mock result within the same transaction. Insufficient stock409 OUT_OF_STOCK or CAS409 CONCURRENT_UPDATE rolls back claim/stock/status/payment; order remains PAYMENT_FAILED. Retry failure restores reacquired qty once, writes one failed attempt; retry success consumes reacquired qty and awards once. Products processed in stable ID order, integer bounds checked; no negative stock, TTL, reservation or background retry.

Success inserts immutable Payment amount=Order.total (Prisma Decimal), PAID/paidAt/version, LoyaltyAward unique/order with floor(total/10000), atomically increments owner balance with INTEGER overflow guard, and clears only snapshot configurations (product + size + sorted topping IDs) in owner's Cart. Purchased qty removed; extra qty/configurations preserved. Missing/insufficient purchased rows are invariant failure/rollback. Cart timestamps and clear commit with payment; lock releases when no active unpaid exists. Existing DB unique success/order, unique request/payment and award/order protect duplicate effects. Failed/cancelled orders never award. COMPLETED is outside B11 and never a second award trigger.

Customer cancel remains B10: PENDING restores once, PAYMENT_FAILED does not restore again, both preserve/unlock Cart, CANCELLED repeat no-op. PAID customer cancel rejected. Payment/cancel/Cart/create serialize on the user lock and status/version CAS; no public paid-cancel/refund/reversal/preparation action added.

Q19 transaction limits: pool wait50ms, transaction400ms, lock200ms, statement300ms. All child writes use the same Prisma transaction client. Frontend confirms server snapshot amount, WALLET/CARD controls, loading/current-state confirmation, failure/retry/cancel; transport uncertainty persists key/payload per user in sessionStorage without JWT, business retry uses new key. Backend decides status.
